# Reference-Led Web Design

Treat the reference as visual evidence. Correct subject matter, matching colors and a long page do not establish visual similarity.

## Resolve what the reference controls

Identify the supplied target and the user's intended fidelity: exact implementation of an owned mockup, a close structural reference, or looser inspiration. Preserve explicit instructions. If this is clear from the request, proceed without another approval step. Do not replace a concrete reference with your preferred aesthetic.

Read the actual reference using the available tools. For a live URL, inspect the current page and relevant behavior; do not infer its design from its name, search snippet or an old report. For screenshots, inspect the image and state the limits of what it reveals. If the target cannot be reached, continue from available evidence and label the result provisional rather than claiming a match.

## Build a comparison map

At matching desktop and mobile widths, capture or measure the areas that determine similarity:

- Header height, logo placement, menu grouping and action placement.
- Container widths, alignment axes, section rhythm and information density.
- Hero composition, photograph crop, text-to-image relationship and first-screen content.
- Type roles, line lengths, wrapping, weight, contrast, color roles, radii and icon treatment.
- Service/product entry points, internal page layout, sidebar, footer and navigation relationships.
- Mobile menu, tabs, forms, overlays, sticky elements and layout transformations.

Use a compact table: **reference observation → intended adaptation → implementation location → rendered evidence → remaining difference**. Distinguish measured facts, choices and unknowns. A copied CSS declaration is not a verified render.

For a whole site, map page families and important paths before implementation. Include internal detail/list/contact/form pages as needed by the brief. Do not inflate the page count with empty templates or rename same-page anchors as separate pages.

## Implement in the right order

Resolve the first viewport and one representative internal screen before propagating the design. Keep the actual deliverable scope in view and continue authorized work; a reviewable slice does not imply a mandatory permission gate.

Recreate layout and interactions using the target project's stack and components. Keep business facts and assets tied to the target brand. Do not silently replace a supplied logo/photo or import another company's claims, customer names, contact details or proprietary assets. Follow explicit rights and scope; private research captures are not automatically redistribution assets.

Forms need state and destination clarity. A local RFQ prototype may collect and export data locally; it must not say “sent” when there is no endpoint. Conversely, do not add intrusive prototype notices to a functioning production path.

## Compare the output, then finish

Render both versions at the same viewport and comparable state. Compare corresponding crops as well as full pages. Fix the largest geometric and hierarchy differences first; changing button color will not correct the wrong hero composition.

Test navigation, one internal path and the principal form/interactive state. Explain deliberate differences and unsupported behavior. Keep technical checks, visual similarity and user/client acceptance distinct. Never call your own review client approval.
