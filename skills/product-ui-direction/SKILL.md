# Product UI Direction

Make the interface recognizably belong to this product. A polished generic template is still the wrong result when the brief asks for a particular brand, reference, or interaction.

## Establish the direction from evidence

- Inspect the real screen, existing components and tokens, official assets, current brief and latest corrections. Historical concepts and implementation notes are evidence of an iteration, not permanent approval.
- Identify the user, the task they came to do, the primary action, the required content and the deliverable: concept, landing page, complete site or working app. Keep that scope visible in your own working notes.
- Write a short design thesis tied to the product: typography roles, density, image treatment, color roles, navigation and one distinctive compositional choice. Explain the choice through the user's task, not adjectives such as “premium” or “modern.”
- Use the user's chosen reference or visual metaphor. An explicitly requested pixel office should remain a pixel office. A retail catalog needs useful product discovery; a B2B service site needs service comprehension and a credible enquiry path.
- When information is discoverable in project files, inspect it before asking. If an optional preference is missing, choose a reversible direction and proceed with a stated assumption. Do not create a new approval round for routine styling.

## Design one convincing slice

Use realistic text and assets to design the first viewport plus a representative task screen or section. Include mobile composition early. Resolve hierarchy, type, image crop and action placement before multiplying the direction across many pages.

For a complete site, map the required page families and navigation. A hero plus service anchors is not a complete corporate website. For an app, include the entry point, main task and result state rather than only a decorative home screen.

Make structure follow content:

- Use tables for comparison or operations, lists for sequences, editorial layouts for reading, grids for browsable items and forms for input. Do not put every sentence inside an identical rounded card.
- Establish clear hierarchy through type, spacing and alignment. Avoid both arbitrary variation and a rigid universal font/spacing recipe. Check real Azerbaijani glyphs and the longest supported labels.
- Use accent color to explain actions and states. Do not substitute another generic palette or erase the requested color in the name of minimalism.
- Prefer exact supplied assets and meaningful imagery. A generated mood image cannot establish a real client, employee, certificate or facility. Keep logo proportions and approved variants intact.
- Keep visible copy specific: what the product does, for whom, what happens next. Use only supported company facts, prices, delivery terms and proof.
- Use motion for feedback or continuity. Respect reduced motion and input method; a routine task should remain immediate. Requested counters or a partner carousel are not automatically slop.

## Implement and verify

Reuse the existing stack and primitives. Preserve working routes, data, validation and authorization. A visual task is not permission to redesign the backend or publish the site.

Render the actual output with real content. Compare the chosen direction at matching mobile and desktop widths; check a primary action and an error/empty state. Use proportional repository checks for the changed code. If rendering is unavailable, distinguish implementation from visual verification.

Deliver the implemented result, the design choices that matter, and what was checked. If the user asked for a review, deliver concrete findings without editing. For worked examples and their limits, read [references/design-examples.md](references/design-examples.md) when a similar case arises.
